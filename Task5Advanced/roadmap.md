# Стратегический роадмап внедрения Data Mesh (36 месяцев)

**Цель:** создать доменно-ориентированную событийную платформу и портал self-service BI без доступа аналитики к медицинским картам, снимкам, историям болезней и результатам исследований.

**Подход:** не разворачивать весь Data Mesh сразу. Начать с общей платформы и двух data products, затем передавать владение данными бизнес-доменам.

## 1. Этапы внедрения

| Срок | Работы | Результат / бизнес-цель |
|---|---|---|
| **0–6 месяцев — пилот** | Назначить владельцев данных; выделить контексты «Финансовые расчёты» и «Пациентский поток»; внедрить Kafka, Schema Registry, Outbox, DLQ; описать каталог и правила приватности; выпустить 1–2 data products и простой отчёт. | Проверить новую интеграцию и сократить время получения пилотных показателей без изменения центрального DWH. |
| **6–18 месяцев — масштабирование** | Подключить финтех, клиники, ИИ (только безопасные метаданные событий), новые направления; запустить Flink / потоковые витрины при подтверждённой потребности; Trino + Power BI + портал; ввести data contracts, владельцев и SLO data products; оставить CDC/Camel как переходные мосты. | Независимый запуск доменов, расширение набора отчётов и первые near-real-time показатели. |
| **18–36 месяцев — целевая эксплуатация** | Перенести логику из DWH в домены; отключить большую часть Camel, SQL Server 2008 и PowerBuilder; автоматизировать контроль качества, управление доступом, аудит, резервирование; закрепить процессы сопровождения доменов и региональные требования. | Слабосвязанная платформа для 2–3 новых регионов, новых продуктов и self-service BI. |

На каждом этапе проводится **контрольная точка**: качество данных, безопасность, стоимость и готовность владельцев доменов. Без прохождения проверки следующий этап не масштабируется.

## 2. Ключевые роли

| Роль | Ответственность |
|---|---|
| **Data Product Owner** (в каждом пилотном/зрелом домене) | Определяет ценность data product, набор показателей, пользователей, SLO и приоритеты. |
| **Data Engineer** (в домене) | Пайплайны, события, контракты, тесты качества и публикация разрешённых данных. |
| **BI-аналитик** | Семантические модели, дашборды, проверка метрик и обучение self-service пользователей. |
| **Platform Engineer / SRE** (центральная команда) | Kafka, Lakehouse, Trino, мониторинг, доступность и эксплуатационные стандарты. |
| **Security / Compliance** | Политики доступа, классификация, аудит, регуляторные и региональные требования. |
| **Архитектор / Domain Lead** | Границы bounded contexts, интеграционные контракты и отказ от зависимости от легаси. |

**Принцип Data Mesh:** домен отвечает за смысл и качество своего data product; платформенная команда предоставляет общие инструменты и политики, но не становится единственным владельцем всей бизнес-логики.

## 3. Пример data products

| Домен | Продукт данных | Потребители |
|---|---|---|
| Клиники | `patient-flow-metrics`: агрегированные показатели посещений и загрузки клиник без медкарт и исследований | Головной офис, BI |
| Финтех | `loan-portfolio-metrics`: разрешённые показатели кредитного портфеля и платежей | Финансовый отдел, BI |
| ИИ | `ai-service-usage`: количество вызовов, время обработки, технические статусы без содержания медицинских исследований | ИИ-команда, BI |

События для междоменной интеграции и data products — **не одно и то же**: домен публикует минимальный безопасный контракт, а продукт данных предоставляет документированные показатели для анализа.

## 4. Метрики успеха (целевые ориентиры для пилота)

| Метрика | Ориентир |
|---|---|
| Time-to-market нового домена | Новая интеграция через стандартный контракт без изменения DWH |
| Время подготовки типового отчёта | Сокращение относительно измеренного исходного времени |
| Задержка доставки событий | Минуты для выбранных near-real-time метрик, по согласованному SLO |
| Качество данных | Контролируемая полнота, актуальность и зарегистрированные ошибки |
| Безопасность | 0 загрузок медицинских карт/снимков/результатов исследований в Lakehouse |
| Экономика | Измеряемый TCO и стоимость обработки/хранения на один data product |
