# Обоснование событийной архитектуры — «Будущее 2.0»

## Почему меняем текущую схему

В текущем ландшафте SQL Server DWH 2008 содержит не только данные, но и бизнес-логику; PowerBuilder и кастомизированный Power BI сильно зависят от него. Apache Camel ESB связывает направления. При добавлении новых клиник, банковских услуг или партнёров приходится менять общую интеграцию и DWH, усложняются тестирование и выпуск функциональности, а тяжёлая аналитика замедляет операционные сценарии.

## Целевое решение

Каждый bounded context (`Patient Registry`, `Clinical Care`, `AI Diagnostics`, `Billing`, `Lending`, `Payments` и др.) владеет бизнес-правилами и своими данными. После значимого изменения агрегата контекст публикует событие через **Transactional Outbox → Kafka → подписчики**. Для контроля схем используется **Schema Registry**, для сбоев обработки — retry/DLQ. Новые контексты (`Pharmacy Orders`, `Medical Devices`) подписываются на нужные события без изменения кода существующих издателей.

Аналитический поток отделён: **разрешённые события → Privacy Projection (классификация/фильтрация/агрегация) → Data Processing (Flink) → Lakehouse (S3/Iceberg) → Trino → портал/Power BI**. Медицинские карты, истории болезней, снимки и результаты исследований в аналитическое хранилище не поступают. Обращение к ИИ для выполнения исследования остаётся защищённой командой/API; итоговое событие сигнализирует об окончании обработки, а не передаёт медицинский результат.

## Сравнение

| Критерий | Текущие Camel + DWH | Целевые доменные события + Kafka |
|---|---|---|
| Связность | Централизованная интеграционная логика и общие схемы | Издатели не знают конкретных подписчиков; контракты событий версионируются |
| Новое бизнес-направление | Новые маршруты/трансформации в общей шине и DWH | Новый bounded context публикует/подписывается на согласованные события |
| Масштабирование | Общая шина и DWH могут стать узким местом | Независимое масштабирование сервисов, consumer groups и потоковой обработки |
| Скорость реакции | Преимущественно пакетная аналитика и тесные интеграции | Near-real-time обработка после публикации события (с учётом задержек) |
| Изменение бизнес-правил | Риск затронуть общую логику DWH | Логика остаётся внутри домена-владельца |
| Отказоустойчивость | Общие точки отказа и тесная цепочка вызовов | Буферизация событий, повторная доставка, DLQ, раздельные сбои потребителей |
| Безопасность | Сложнее ограничить использование общего хранилища | Отдельные хранилища и ACL; аналитика только через Privacy Projection |

## Ограничения и меры

- **Eventual consistency:** разные домены могут видеть изменения не одновременно. Для распределённых процессов использовать Saga, компенсации и отслеживание статусов.
- **Дубликаты / потеря событий:** Outbox + CDC, идемпотентные подписчики, дедупликация по `event_id`, retries, DLQ и мониторинг.
- **Эволюция контрактов:** Schema Registry, совместимые версии, контрактные тесты и явные владельцы событий.
- **Чувствительные данные:** минимальный payload, разделение топиков и прав, Privacy Projection, аудит, соблюдение требований локализации и регуляторов.
- **Сложность эксплуатации Kafka/Flink:** наблюдаемость (lag, DLQ, задержка витрин), инфраструктура как код, нагрузочные тесты, резервирование.
- **Синхронные операции не запрещены:** проверки и запросы, требующие немедленного ответа (например, защищённый запуск ИИ-исследования), остаются API/командами; события служат для оповещения о завершённых фактах.
